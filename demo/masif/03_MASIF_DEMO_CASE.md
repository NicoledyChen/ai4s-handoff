# MaSIF binder：从 AI 探索成果到稳定工作流

版本：产品化演示 v0.2 · 2026-09-10。用途：给投资人讲清已有 AI 探索成果如何沉淀为产品，并给丹阳、林洁及设计同事提供场景、文案与素材清单。

本案例聚焦第 4、8、11、12 环节。用户提供的 Word 记录了团队用 AI 实际运行 MaSIF 探索的成果；现在的目标是把这段真实流程沉淀为 Skills，使框架稳定跑出非常接近的工作轨迹，并提供用户能协作和追溯的界面。具体交互与候选样例的来源边界集中说明于文末。

配套：[基础设施架构](01_INFRA_ARCHITECTURE.md)、[用户体验与哲学](02_UX_PHILOSOPHY.md)。

宣讲架构配图：[infra 架构](diagrams/01-infra-architecture.png)、[Agent 框架](diagrams/02-agent-framework.png)，均有同名 SVG 可供后续修改。

## 1 投资人需要记住的故事

团队已经通过 AI 跑通 binder 设计探索。下一步用 Skills 固化输入、参数、决策与产物合同，把一次探索变成可稳定承接的工作流。Agent 接住数据整理、工具衔接和结果解释；在会改变设计方向、可修改范围、候选组合或计算预算的地方，把证据与选择交还给科学家。

用户不需要盯着每个工具，但随时能点名角色、圈选结构、展开依据，并把工作留在自己的结构文件、脚本和计算环境中。

这次展示的核心转折：

> 团队实跑报告中，筛选后有 633 个嫁接候选，却只来自 3 个 seed 来源。app 帮助用户看懂数量背后的冗余、保留不同结构假设，再检查候选是否仍落在目标位点。

商业价值落在减少工具间搬运、减少无依据的重复计算、使关键判断可操作与可回查。不宣称提高了多少实验命中率或缩短了多少研发周期。

## 2 团队已经跑出的科学工作轨迹

### 团队实跑成果

来源是团队用 AI 实跑后形成、由用户提供的《MaSIF binder 设计全流程与人工选择指南》。原文以 canine trka af3 A 为实例；对外展示暂用 Target-A。

以下数量作为团队探索成果正常展示：

| 阶段 | 团队实跑报告 | 正确解释 |
|---|---|---|
| MaSIF 搜索 | 208 个匹配 | site 0 为 194，site 1 为 14 |
| 聚类代表 | 60 个 | 6 类，每类 10 个 |
| Rosetta 后续筛选 | 13 个 seed/motif | 经第 9 环节筛选后进入嫁接，不是第 8 环节的全部输出 |
| 嫁接产物 | 1864 个可解析构象 | 由嫁接产生扩增 |
| 嫁接筛选 | 633 个 | 只来自 3 个 seed ID，具体占比未提供 |
| AF3 输入 | 150 个复合物 | 每个输入使用一个 model seed；不是验证成功数 |

不能把 208 → 60 → 13 → 1864 → 633 → 150 画成单调缩小的漏斗。对象类型不同，而且 13 → 1864 是生成扩增。

产品化要继承这条轨迹中的判断依据、失败处理和计算边界，而不只是复刻最终数字。

## 3 把四个环节沉淀为 Skills 与用户协作节点

| 节点 | 用户在做什么 | 任务 Agent 承载什么 | 主结果对象 | 进入下一步之前 |
|---|---|---|---|---|
| N1 第 4 环节 | 确认设计针对哪个表面区域 | 表面结果整理、位点比较、可视化与约束记录 | SiteDecision | 明确 site、可选残基限制与允许偏移 |
| N2 第 8 环节 | 确认哪些部分可改 哪些必须保留 | 链/残基规则检查、配置提案、运行衔接与前后叠合 | DesignPolicy + RunBundle | 确认链角色、设计范围、柔性与预算 |
| N3 第 11 环节 | 从候选数量转向候选质量与差异 | 多指标筛选、来源去冗余、结构比较 | CandidateSet | 确认母体集合、来源配额和选择理由 |
| N4 第 12 环节 | 判断是否可信 是否需要补算或退回 | 设计与预测对照、异常归纳、复核计划 | ValidationBundle | 处理位点冲突，确认新增复核范围与预算 |

这不是四个拟人科学家。首版使用三个可寻址角色即可：

- 分析 Agent：整理指标、候选、来源和异常，管理分析信息的多个层级。
- 可视化 Agent：管理表面、结构叠合、候选比较及图形的多个层级。
- 流程 Agent：管理任务依赖、参数版本、交付、预算请求和检查点。

同一角色可以贯穿多个节点；MaSIF、Rosetta、MotifGraft 和 AF3 是底层工具/流程，不要求各自变成一个人格。

四节点 Skill 映射：N1 固化位点输入、链与表面约束，产出 SiteDecision；N2 固化设计边界、参数版本和批准范围，产出 DesignPolicy／RunBundle；N3 固化筛选依据、候选谱系与来源配额，产出 CandidateSet；N4 固化验证证据、冲突处置和补算条件，产出 ValidationBundle。

这里的“稳定”指输入／参数／决策／产物合同一致、检查点明确、失败可恢复，在相近条件下得到非常接近的执行轨迹；不要求 Agent 回复逐字相同，也不要求随机计算的候选或数值完全一致。Skills 与版本化产物共同承载团队已经积累的经验。

## 4 N1 选位点时把科学意图表达清楚

**用户问题**

“先让我看看这两个候选位点；这次还没有指定必须覆盖的功能残基。”

**画面主体**

Target-A 的表面视图，两个 site 可切换；右侧是位点目的与约束卡，而不是几十个高级参数。

团队报告中的设置是保留两个 site、未启用 target residue、覆盖半径未固定。

**群聊节奏**

- 可视化 Agent：“我把两个位点放在同一结构视图里。你可以分别检查覆盖区域，site ID 本身不代表质量。”
- 分析 Agent：“当前还没有指定功能残基。是否保留两个位点并分别记录后续结果？”
- 用户：“这一轮先保留两个，不增加残基限制。”

**交互结果**

保存一个绑定结构与链版本的 SiteDecision，包含选择、限制和未确定的信息。展开结构是 PULL；确认用于后续搜索是新的决策记录，二者不混同。

Skill 检查结构、功能目的与必要约束；必需输入不完整时保存草案，不启动搜索。

点击“下一检查点”进入 N2，阶段5–7的搜索、诊断和聚类保留在流程轨迹中。

**产品表达**

自然语言里的设计意图被转成工具能够继承、以后可以检查的工作约束。

## 5 N2 让可修改范围成为可视的执行边界

**用户问题**

“先让我确认 target、binder 和 motif 各自允许改什么，再继续。”

**画面主体**

左右结构叠合与区域图例：固定序列、可设计区域、保护的 motif、允许的骨架变化分别表达。另有配置差异卡与资源请求状态。

原文实例中 target 序列不变，但骨架设置为 target 可动、binder 固定。因此不能把界面画成“target 完全冻结”；实际哪些区域可动须由研发提供配置与结构核对。

**群聊节奏**

- 流程 Agent：“这里把序列规则和骨架规则分开列出。当前文档允许 target 骨架变化，但不设计其序列。”
- 可视化 Agent：“保护区域与可变区域已用不同图层呈现；缺少真实残基映射的部分标为待确认。”
- 用户：“规则按这一版确认；任何扩大设计范围或预算的变更再问我。”

**交互结果**

保存 DesignPolicy 的版本与批准范围，随后可展开 Rosetta 结果、参数与日志的对应关系。

执行 Skill 检查完整链／残基映射、配置和预算，使群聊中的批准对应可执行边界。

一个可演示的产品细节：用户修改了设计范围后，旧的批准卡标为“已失效 待重新确认”。

**桥接**

说明第 9 环节执行联合筛选，第 10 环节进行嫁接扩增；演示快进到 N3，不把这两步从科学流程中删掉。

**产品表达**

自动化承接机械执行，但用户仍能看懂并控制“允许系统改什么”。

## 6 N3 用候选多样性引出 app 的判断价值

**先显示团队成果摘要**

“团队实跑：1864 个可解析嫁接构象，筛选保留 633 个，只有 3 个 seed 来源。”

展开来源时，可查看报告依据及来源占比、全量候选表的接入状态。

**用户追问**

“633 个看起来很多，我们是不是已经有足够多的方案？”

**群聊节奏**

- 分析 Agent：“总数不等于独立方案数。还需要比较 seed 来源、scaffold 折叠和界面模式。”
- 可视化 Agent：“先按来源和结构差异比较，再看分数。打开候选比较视图。”
- 用户：“给我保留不同结构假设，不要直接按一个总分取前几名。”

**候选交互样例**

| 候选 | 样例来源 | 样例结构家族 | 用于讲解的状态 |
|---|---|---|---|
| DEMO-M01 | DEMO-SEED-A | DEMO-FOLD-X | 有吸引力的候选，等待设计与预测一致性检查 |
| DEMO-M02 | DEMO-SEED-A | DEMO-FOLD-X | 与 M01 同来源同家族，用来解释冗余 |
| DEMO-M03 | DEMO-SEED-B | DEMO-FOLD-Y | 不同结构假设，用来解释多样性 |
| DEMO-M04 | DEMO-SEED-C | DEMO-FOLD-Z | 证据不完整，用来解释保留待定项 |

**用户选择**

演示分支将 M01 与 M03 标记为“进入复核”；M02 保留为未选备选并记录冗余理由；M04 标为待补材料。操作可撤销，四条记录始终可查看。

**产品表达**

用户可以看到选择的依据与损失，而不是被一个不透明的综合分排名牵着走。

## 7 N4 用高置信但错误位点展示弱黑箱

用一个候选交互样例说明：如何处理置信度与设计意图的冲突。

**画面主体**

设计结构与 AF3 预测结构的叠合区域；右侧并列展示位点一致性、模型置信度、结构问题和重复检查状态，并提供 PAE 等证据入口。

**剧情**

- DEMO-M01：设置为“预测置信度较高，但偏离原设计位点”的示意冲突。
- DEMO-M03：设置为“未观察到该示意冲突，但重复一致性尚未检查”。
- 两者都不能直接标“结合成功”或“实验候选已验证”。

**群聊节奏**

- 分析 Agent：“M01 的置信度与位点一致性发生冲突。不能只看最高分。”
- 可视化 Agent：“我把原设计区域与预测接触区域分开显示，你可以展开叠合与来源。”
- 用户：“M01 先退回复核；M03 保留待进一步检查。新增计算先给我预算方案。”
- 流程 Agent：“已记录这个选择。补充计算只是提案，尚未提交。”

**演示结果**

M01 从复核队列退回带理由的待处理状态；M03 保留，标记尚无多 model seed 一致性证据。新预算未确认时工作停在可恢复的提案状态。

这里要区分：

- seed 来源：候选结构从哪里来。
- model seed：预测的随机种子。

原文 AF3 实例每个输入只有一个 model seed，无法据此展示多次预测一致性结论。若以后拿到真实重复运行结果，再替换相应证据面板。

**产品表达**

弱黑箱不是解释模型脑内怎么想，而是让输入、工具结果、冲突、人的选择与下一步都能检查。

## 8 四屏草图与共用布局

延续 Lumen 的群聊、结果工作面、inspector 与原始来源，把 Skill 执行轨迹连接到同一用户界面，不另设计一个科研 IDE。

建议先画四张主屏，共用一套框架：

~~~text
┌──────────────────────────────────────────────────────────────────┐
│ Target-A  | AI 探索工作流  | Skill 版本  | 来源与执行详情          │
│ [N1 位点] ─ [N2 设计边界] ─ [N3 母体选择] ─ [N4 复核]             │
├─────────────────┬────────────────────────────┬───────────────────┤
│ 角色与群聊      │ 当前结果工作面             │ 决策/证据抽屉     │
│                 │                            │                   │
│ 分析            │ 当前对象与版本             │ 当前状态与限制    │
│ 可视化          │ 大结构图 / 候选比较        │ 选择及其后果      │
│ 流程            │                            │                   │
│                 │ [摘要][工作面][分析][来源] │ [确认范围]        │
│ 关键交接与追问  │                            │ [暂缓/保留待定]   │
│ @角色 输入问题  │ 点击/圈选绑定当前对象      │ [打开原始记录]    │
└─────────────────┴────────────────────────────┴───────────────────┘
~~~

这里“确认范围”随节点变化，不是一个永久授权按钮。Signal 体现在导航/卡片状态，不必把五级全部做成五个占地方的标签页。

### 主屏 S1 对应 N1

~~~text
中心：Target-A 表面示意
      [site 0] [site 1] [叠合查看]
右侧：设计意图
      保留位点：2个（文档实例）
      功能残基限制：未设置
      可接受偏移：待确认
      [保存位点选择]
群聊：可视化解释覆盖，分析询问意图
~~~

需要画出的交互：点 site 会同时改变中心高亮和右侧对象信息，不产生新的科学计算；保存决定才改变下游任务约束。

### 主屏 S2 对应 N2

~~~text
中心：原始/优化结构对照位
      [序列规则] [骨架规则] [保护 motif]
右侧：设计边界 v1
      Target序列：不改
      Target骨架：按源配置核对
      Binder设计：按残基规则
      预算：待提供/模拟状态
      [确认此版本的范围]
群聊：流程明确哪些改变会让旧确认失效
~~~

最重要的是不把“固定序列”画成整条链完全不能动；规则和图层分别表达。

### 主屏 S3 对应 N3

~~~text
中心上：633候选 / 3个seed来源（团队实跑报告）
        [查看来源详情]
中心下：候选交互样例
        M01 [A/X]   M02 [A/X]
        M03 [B/Y]   M04 [C/Z · 待补证据]
右侧：当前选择 M01 + M03
      M02 未选理由：同来源同家族示意
      M04 保留待定
      [保存选择与理由]
群聊：讨论不同结构假设，而非只取最高分
~~~

团队结果摘要与候选交互样例各自保留来源入口。

### 主屏 S4 对应 N4

~~~text
中心：设计与预测叠合示意
      M01：置信度与位点发生冲突
      M03：尚无重复一致性证据
右侧：处置提案
      M01 退回复核
      M03 保留待进一步检查
      新增预算尚未批准
      [记录处置] [查看证据] [打开原始文件]
群聊：提出补充检查，但不擅自启动计算
~~~

再加一张可复用的证据抽屉特写即可：从 M01 点进去能看到输入引用、配置版本、结构来源、运行状态、选择理由与未决事项。

## 9 同一个候选如何逐级展开

以候选交互样例 DEMO-M01 为例：

- Signal：“需要判断：设计位点与预测位点不一致。”
- Summary：“模型置信度不能消除位点冲突；建议先复核，不直接入选。”
- Workbench：设计/预测叠合，打开不同图层，与 M03 对照。
- Analysis：位点检查、指标冲突、是否有重复运行及目前不能下的结论。
- Source：对应输入、参数、原始结果和人的处置记录；示意缺项明确写未提供。

分析 Agent 维护解释与证据层级，可视化 Agent 维护结构表达与图层，流程 Agent 维护真实执行/提案状态。程序校验来源、版本、受众和不可省略字段。

主展示聚焦科学工作与协作，候选区保留简洁的“交互样例”说明；完整数据来源和执行状态统一在来源抽屉与文末说明，不以大幅警示反复打断。

## 10 三分钟讲解脚本

| 时间 | 展示动作 | 讲给投资人的话 |
|---|---|---|
| 0:00–0:20 | 打开 Target-A 工作 | “团队已用 AI 跑通这段探索；现在把经验沉淀成 Skills，让它成为稳定、可协作的产品。” |
| 0:20–0:45 | N1 选位点 | “用户表达设计意图，Agent 把它变成后续步骤能继承的约束。” |
| 0:45–1:10 | N2 查看可改范围 | “自动化之前，哪些东西能改是明确的；换了范围，旧的确认就不再适用。” |
| 1:10–1:50 | N3 展示633与3 再开候选比较 | “团队的实跑结果揭示：大量候选可能只是重复。用户能看见不同选择代表什么。” |
| 1:50–2:30 | N4 点开示意冲突 | “高置信度不等于满足设计意图。系统把冲突交给用户，而不是只回一个最好结果。” |
| 2:30–3:00 | 展开 Skill、来源与检查点 | “稳定来自输入、参数、决策、产物的合同和可恢复路径。智能可以替换，团队的工作与判断不丢。” |

这段演示把团队已有的探索成果连接到可重复执行的产品路径；效率、成本与命中率收益仍需另行测量。

## 11 需要你和林洁提供什么

以下分工是便于沟通的建议，不是假定谁拥有某项材料；由你们按实际情况分配。

### 画第一版草图最少需要

1. **可对外展示的目标结构素材。** 最好一张 target 表面及两个 site 的图，并确认真实名称是否可用；缺失时继续用 Target-A 示意。
2. **一组前后结构对照。** Rosetta 优化前后、设计结构与 AF3 预测各一例，能标出链与关注区域；如果只有截图也可先画。
3. **真实的工作口吻与判断。** 请确认四处最值得展示的“人为什么要介入”，并告诉我们示意冲突是否贴近研发实际。

没有这些也能画当前信息结构，但不能宣称图形是真实项目结果。

### 把已有成果接入结构证据与实际执行需要

- 一个完整候选的谱系：target/site → 来源 seed → Rosetta → scaffold/嫁接 → AF3；附真实 ID 与对应文件。
- 候选评分表、seed/scaffold 来源映射及筛选记录，特别是 633 条的构成与 150 条的实际选择依据。
- AF3 的真实结构、置信度与 PAE 等原始输出；如要展示多 model seed 一致性，需提供对应多次运行结果。
- 一份脱敏配置/日志，注明代码或工具版本、运行环境以及可公开范围。
- 实际预算/执行入口/权限边界。没有数据就不显示精确“节省了几小时、几块钱”。

### 平台侧最低确认

现有 app 能否加载外部结构 viewer、渲染表格/图形、保存对象版本、点名角色与打开原生文件；哪些是真实能力，哪些需要前端模拟。当前已知 Lumen 是静态原型，不默认拥有这些后端接口。

## 12 演示包的实现与验收边界

先把已有实跑轨迹与检查点映射到可交互界面，再把 Skills 接到实际工具和计算环境。界面选择、展开、对比和记录理由可独立实现；后端接通后，沿同一输入、参数、决策与产物合同执行。

配套 [demo-fixtures.json](demo-fixtures.json) 保存团队报告聚合数字、四条候选交互样例、节点与处置脚本，供设计和开发统一命名；具体数据层级与执行状态见下方来源说明。

最小验收：

- 第 4、8、11、12 环节准确对应；中间步骤及 Skill 合同保留在可追溯轨迹中。
- 团队实跑事实、交互样例和当前执行状态可分别查明；主展示不重复大幅警示。
- 修改设计范围后，旧决策不继续被当作有效授权。
- 未选候选及选择理由可回查；未知与未复核不被写成失败或成功。
- 任何“来源”按钮都打开真实存在的材料，或明确标未提供；不伪造成功读取。
- 最终交付是计算复核与下一步提案，不是实验成功、临床价值或产品化 binder。

## 附 来源、界面编排与接入范围
